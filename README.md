# infra-monitoring-project

Учебный проект для проверки доступности API, анализа логов
и запуска сервиса через Docker Compose.

## Основные файлы

- `check_api.sh` — проверяет доступность API по HTTP-коду ответа.
- `analyze_logs.sh` — создаёт тестовый лог и выводит статистику запросов.
- `docker-compose.yml` — описывает контейнеры API и nginx.
- `nginx.conf` — содержит настройки проксирования запросов.
- `.github/workflows/ci.yml` — содержит проверки GitHub Actions.
- `.gitignore` — исключает ненужные файлы из Git.

## Что нужно для запуска

Для работы нужны Git, Bash, curl, Docker и Docker Compose.

На macOS можно использовать Docker Desktop. Перед запуском
контейнеров приложение должно быть открыто.

## Подготовка проекта

Клонирование репозитория:

```bash
git clone https://github.com/ivanovamm/infra-monitoring-project.git
cd infra-monitoring-project
git switch feature/monitoring
```

Если проект уже скачан, достаточно перейти в его папку.

Разрешение на выполнение скриптов:

```bash
chmod +x check_api.sh analyze_logs.sh
```

Все локальные команды ниже выполняются из корня проекта.

## Проверка доступности API

Скрипт принимает URL как аргумент. Если сервер отвечает кодом
200, скрипт выводит сообщение о доступности и возвращает код 0.
При другой ситуации возвращается код 1.

Пример успешного запроса:

```bash
./check_api.sh https://httpbin.org/status/200
echo $?
```

Ожидаемый результат:

```text
API доступен
0
```

Пример запроса с ответом 404:

```bash
./check_api.sh https://httpbin.org/status/404
echo $?
```

Ожидаемый результат:

```text
API недоступен, код ответа: 404
1
```

Пример неправильного URL:

```bash
./check_api.sh not-a-url
echo $?
```

В этом случае скрипт сообщит об ошибке в аргументе
и завершится с кодом 1.

Команда `echo $?` показывает код завершения предыдущей команды,
поэтому её нужно выполнять сразу после запуска скрипта.

## Анализ логов

Запуск:

```bash
./analyze_logs.sh
```

Если файла `access.log` нет, скрипт создаёт тестовый лог
из 360 строк. Если файл уже существует, анализируется его содержимое.

Скрипт выводит:

- общее количество запросов;
- три IP-адреса с наибольшим количеством запросов;
- количество ответов с кодами 4xx и 5xx.

Для поиска IP-адресов используется регулярное выражение.
Обработка данных выполняется с помощью grep, awk, sort и uniq.

Пример результата для сгенерированного лога:

```text
Общее количество запросов: 360
Топ-3 IP-адреса:
  192.168.1.10 — 120 запросов
  10.0.0.5 — 90 запросов
  192.168.1.20 — 60 запросов
Количество запросов 4xx: 72
Количество запросов 5xx: 36
Всего ошибок 4xx и 5xx: 108
```

Проверка количества строк:

```bash
wc -l access.log
```

Повторное создание тестового лога:

```bash
./analyze_logs.sh --generate
```

Параметр `--generate` перезаписывает существующий тестовый лог.

## Запуск через Docker Compose

В проекте используются два сервиса:

- `api` — готовый образ hashicorp/http-echo, который отвечает
  текстом `Monitoring Service Active`;
- `proxy` — nginx, который принимает запросы на порту 80
  и передаёт их сервису api на порт 8080.

Контейнеры связаны общей сетью `monitoring`.

Проверка конфигурации:

```bash
docker compose config
```

Запуск контейнеров в фоновом режиме:

```bash
docker compose up -d
```

Проверка состояния контейнеров:

```bash
docker compose ps
```

Проверка ответа сервиса через nginx:

```bash
curl http://localhost:80
```

Ожидаемый ответ:

```text
Monitoring Service Active
```

Этот же адрес можно проверить своим скриптом:

```bash
./check_api.sh http://localhost:80
```

Просмотр логов контейнеров:

```bash
docker compose logs
```

Остановка и удаление контейнеров проекта:

```bash
docker compose down
```

## Проверки GitHub Actions

Workflow находится в `.github/workflows/ci.yml`.

При создании Pull Request в main запускаются автоматические
проверки синтаксиса Bash-скриптов и проверка API с ожидаемым
ответом 200.

Синтаксис можно проверить локально:

```bash
bash -n check_api.sh
bash -n analyze_logs.sh
```

Результаты автоматических проверок доступны во вкладке
Actions на GitHub.

## Передача проекта на сервер через SSH и SCP

Ниже приведён пример команд для развёртывания проекта
на удалённом Linux-сервере.

В примерах `SERVER_IP` нужно заменить на адрес сервера,
а `deploy` — на имя существующего пользователя сервера.

На сервере должны быть установлены Docker и Docker Compose.
У пользователя должен быть доступ по SSH и право запускать Docker.

### 1. Создание SSH-ключа

На своём компьютере создаю отдельный ключ для проекта:

```bash
mkdir -p ~/.ssh
ssh-keygen -t ed25519 -f ~/.ssh/infra_monitoring -C "infra-monitoring-project"
```

При создании ключа задаю парольную фразу.

Будут созданы два файла:

- `~/.ssh/infra_monitoring` — закрытый ключ;
- `~/.ssh/infra_monitoring.pub` — публичный ключ.

Закрытый ключ остаётся на моём компьютере и не добавляется
в репозиторий. На сервер передаётся только публичный ключ.

Если ключ с таким именем уже существует, повторно создавать
и перезаписывать его не нужно.

### 2. Копирование публичного ключа

```bash
ssh-copy-id -i ~/.ssh/infra_monitoring.pub deploy@SERVER_IP
```

Для первого входа потребуется действующий доступ к серверу,
например пароль пользователя deploy.

При первом подключении нужно сверить отпечаток SSH-ключа
сервера с данными администратора или панели управления сервером.
После проверки можно подтвердить подключение.

### 3. Создание архива проекта

На своём компьютере, из папки проекта, создаю архив:

```bash
git archive --format=tar.gz --output=../infra-monitoring-project.tar.gz HEAD
```

В архив попадут файлы последнего коммита текущей ветки.
Поэтому перед созданием архива все нужные изменения
должны быть сохранены в Git.

Архив будет находиться рядом с папкой проекта.

### 4. Передача архива на сервер

```bash
scp -i ~/.ssh/infra_monitoring ../infra-monitoring-project.tar.gz deploy@SERVER_IP:~/
```

Архив копируется в домашнюю папку пользователя deploy
на удалённом сервере.

### 5. Запуск проекта на сервере

Сначала подключаюсь к серверу:

```bash
ssh -i ~/.ssh/infra_monitoring deploy@SERVER_IP
```

Следующие команды выполняются уже на сервере.

Создание папки и распаковка архива:

```bash
mkdir -p ~/infra-monitoring-project
tar -xzf ~/infra-monitoring-project.tar.gz -C ~/infra-monitoring-project
cd ~/infra-monitoring-project
```

Запуск и проверка контейнеров:

```bash
docker compose up -d
docker compose ps
curl http://localhost:80
```

Здесь localhost означает удалённый сервер,
поскольку команды выполняются после подключения по SSH.

При успешном запуске должен вернуться ответ:

```text
Monitoring Service Active
```

Завершение SSH-соединения:

```bash
exit
```
